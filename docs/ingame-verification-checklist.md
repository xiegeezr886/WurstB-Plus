# 实机验证清单（hud2 / ESP）

## 这份清单为什么存在

`docs/openaopal-hud-research.md` 记录的是「做了什么、为什么这么做」。这份记录的是
**「哪些东西到现在一次都没在游戏里看过」**。

到目前为止所有 hud2/ESP 的外观工作**没有一项经过实机验证**——全部只有逻辑核对与
单元测试。测试能证明「算出来的数对」，不能证明「画出来好看、位置对、不重叠、不挡
鼠标」。下面按「错了后果最严重」排序。

## 怎么进

- **HUD 编辑器**：Wurst 选项界面里的按钮（`WurstOptionsScreen.java:104`），或
  ClickGUI 里的对应入口（`SuperSoftClickGuiScreen.java:476`、`EpsilonDropdownScreen.java:649`），
  或 `ScreenRegistry.java:47` 注册的那个入口。
- **布局与元素设置文件**：`<wurst 文件夹>/hud-layout.json`。元素设置也写在这里，
  键名是**设置名的全小写**（例如 `"text color"`、`"key size"`、`"equipment"`）。
- 若某一项看起来是「完全没反应」，先看游戏日志里有没有 `[PostEffect] Disabling ...`
  或着色器编译报错——有几种失败是**静默降级**的（见第 6 项）。

## 1. 设置面板（风险最高：整套 UI 是新的，测试只覆盖了命中数学）

1. 打开 HUD 编辑器，把鼠标**悬停**在任意元素上。
2. 右下角、工具栏上方应出现一个设置面板。
3. 逐个看：

| 行类型 | 元素 | 期望 |
|---|---|---|
| 勾选框 | 目标信息（TargetHUD）的 `Equipment` | 点一下切换，勾选状态看得出来 |
| 枚举 | 有名枚举设置的元素 | 点一下切到下一个值，值文字用强调色 |
| 滑条 | 键位（Keystrokes）的 `Key size` | 行下沿有一条轨道，点/拖跟着走，值文字是整数如 `21` |
| 颜色 | 任意文字元素的 `Text color` | 右侧一个色块；点一下**打开取色屏**，关掉回到编辑器 |

**具体要确认的**：
- 轨道和上面的文字**挤不挤**（面板只有 196 宽、行高 20）。
- 面板会不会**挡住它下面的元素**，导致那个元素点不到。
- **在滑条上按住并拖动时，元素本身会不会跟着动**——不应该动。这是本轮最容易写错
  的一处（`HudEditorScreen.mouseDragged` 里面板优先），请专门试一下。
- 拖完滑条松手后再关编辑器，重开，值应该还在。
- 取色屏回来后，设置面板**还在不在**（应该还停在同一个元素上）。

## 2. 键位元素尺寸（`Key size` 滑条：常量改成了实例方法）

把 `Key size` 拖到最小 **12** 和最大 **36**，各看一眼：
- 键帽不会互相重叠、不会跑到面板外面。
- 空格键/Shift/CPS 那几行的宽度仍然对齐（它们由 `width()` 推导）。
- `getWidth()/getHeight()` 变了以后，编辑器里元素的选中框跟着变，**拖动和点击
  的位置仍然对得上**（这是把 `static final` 改成实例方法后最容易错的地方）。

> 背景：`KEY_SIZE`/`WIDTH`/`HEIGHT` 原来是 `static final` 常量，为了接滑条改成了
> 实例方法。尺寸与布局**全是推导的**，我一次都没看过。

## 3. 9 个文字元素的默认颜色（默认值必须和以前一模一样）

FPS、坐标、时钟、Ping、服务器、速度、TPS、连击、SoarText —— 这 9 个的着色来源从
常量 `VisualTheme.TEXT` 改成了 `ColorSetting`，默认值取 `(255,255,255)`。

**要确认的是：它们和以前看起来完全一样。** 我的理由是「新默认值数值上等于旧常量」，
推理是对的，但**数值相等不等于肉眼无差别**（渲染路径对 alpha 的处理、颜色分量顺序
都可能不一样）。这是本轮我最没底的一处。

顺便试一下把某个的 `Text color` 改成半透明，看透明度**有没有生效**——绘制用的是
`getColor().getRGB()` 而不是 `getColorI()`，就是为了不把 alpha 强制成不透明。

## 4. 目标信息（TargetHUD）的装备行与双色血条

- 装备行画在血条**下方那条空带**里，图标不糊、不超出面板。
- 血条是**两层**：受伤时应该看到底下滞后暗色条的拖尾。
- 「满血 + 满吸收」时血条是**满的**（比例把吸收同时算进分子与分母）。
- 血条上的数字是「生命 + 吸收」的合计。
- 把 `Equipment` 勾选框关掉，装备行应该消失。

## 5. ESP 名字标签（Skia 通道）

- 名字标签的位置、字号（5）、行距、背景圆角、图标在右侧。
- 状态图标：潜行/隐身/格挡 三个汉字图标，顺序是 **潜行 → 隐身 → 格挡**。
- 附魔短名（39 项映射）显示是否可读。

**兜底路径在 Windows 上大概率看不到**：Skia 不可用时才走 vanilla 绘制的兜底
（`PlayerEspHack` 的 `renderNameTagsVanilla`）。本机有 `skiko-windows-x64.dll`，
所以正常情况走的是 Skia。**这个兜底路径实际上仍然从未被执行过**——如果哪天在别的
平台上跑，它是第一嫌疑人。

## 6. Bloom（TargetShader hack）

打开 **TargetShader** hack，把 `Effect` 设为 **Bloom**，锁定一个目标。

- 期望：目标周围有一圈**很宽、渐隐**的光晕（三圈稀疏环形采样）。
- **如果完全没效果**：很可能是 GLSL 编译失败，而它被**静默降级**了——
  `PostEffectQueue` 把失败的效果记进 `failedEffects` 并永久停用，只打一行
  `[PostEffect] Disabling Bloom after initialization/render failure: ...`。
  **请把日志里那一行发我**，那是唯一能定位着色器问题的线索。
- 顺便和另外 4 个已有效果（Outline/Pulse/Gradient/Smoke）比一下，确认我没把
  它们的观感改坏——我把 `smoke` 从 `else` 改成了显式 `Mode == 3`。

## 7. 设置的持久化往返

1. 在编辑器里改几项（勾选框、滑条、颜色各一）。
2. **完全退出游戏**（不是只关编辑器）。
3. 打开 `<wurst 文件夹>/hud-layout.json`，确认有 `settings` 段、且值是你改的。
4. 重进游戏，确认值是改过的样子。

> 背景：`init()` 从「有位移才存盘」改成了**无条件存盘**，`onClose()` 也加了一次。
> 原因是元素设置只写在 `hud-layout.json` 里，取色屏那条路径原来要等到退出游戏才落盘。
